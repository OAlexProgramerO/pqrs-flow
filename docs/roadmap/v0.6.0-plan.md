# PQRS Flow — Plan de versión v0.6.0

**Estado:** implementación candidata. Las 500 pruebas backend y los chequeos locales de ESLint/Prettier pasan; la auditoría de dependencias y CI deben ejecutarse en el entorno objetivo.
**Versión objetivo:** `0.6.0`
**Base requerida:** `main`, después de integrar y validar el PR de `feature/v0.5.1-auth-hardening`.

## 1. Objetivo

Convertir las mejoras de autenticación en una experiencia administrativa más segura, verificable y fácil de operar. El foco será completar el ciclo de MFA, hacer utilizable la auditoría de seguridad y reforzar pruebas y documentación.

## 2. Alcance propuesto

### 2.1 Autenticación multifactor y recuperación

- Revisar y documentar la configuración, activación, validación y desactivación de TOTP.
- Diseñar un procedimiento seguro de recuperación para administradores que pierdan su dispositivo MFA.
- Evaluar códigos de recuperación de un solo uso, si el diseño de seguridad lo permite.
- Evitar que secretos TOTP, códigos, contraseñas, cookies o tokens aparezcan en logs o respuestas.
- Verificar que las acciones sensibles requieran sesión válida y permisos adecuados.

**Aceptación:** pruebas automatizadas para flujos correctos, errores, intentos inválidos y recuperación; ningún secreto se devuelve ni se registra.

### 2.2 Auditoría de seguridad

- Normalizar los eventos de inicio de sesión, bloqueos por rate limit, cambios de MFA y acciones administrativas sensibles.
- Registrar solo los metadatos necesarios y excluir datos secretos.
- Incorporar límites y paginación a las consultas de eventos.
- Documentar acceso, retención y tratamiento de los registros.

**Aceptación:** pruebas de persistencia, autorización y ausencia de secretos en los eventos.

### 2.3 Interfaz administrativa

- Evaluar una sección de seguridad en `frontend-admin` para consultar los eventos autorizados.
- Añadir filtros básicos por tipo, resultado y rango temporal, si la API lo permite.
- Mostrar estados de carga, error y ausencia de resultados.
- Mantener accesibilidad, diseño adaptable y la navegación existente.
- No mostrar tokens, cookies ni secretos en pantalla.

**Aceptación:** las vistas manejan errores de API, permisos insuficientes, respuestas vacías y paginación.

### 2.4 Pruebas y dependencias

- Añadir pruebas de integración para autenticación, MFA, rate limiting, eventos y migraciones.
- Comprobar migraciones tanto en bases de datos nuevas como existentes.
- Mantener `npm run check` como control obligatorio.
- Ejecutar `npm --prefix backend audit --omit=dev --audit-level=high`.
- Verificar compatibilidad con las versiones de Node indicadas por `.nvmrc` y CI.

**Aceptación:** todas las comprobaciones pasan en CI sin ocultar errores ni saltarse hooks.

### 2.5 Documentación

- Actualizar `docs/security.md` con MFA, recuperación, sesiones y eventos.
- Actualizar `docs/architecture.md` si cambia la arquitectura.
- Documentar nuevas variables en `.env.example`, sin valores reales.
- Actualizar `CHANGELOG.md` solo con cambios implementados y verificados.
- Mantener `README.md` y `README.es.md` alineados cuando cambie el comportamiento visible.

## 3. Fuera de alcance

Salvo aprobación explícita, esta versión no incluirá una reescritura completa, migración de base de datos, integración obligatoria de OAuth/SSO, despliegue automático a producción ni cambios no relacionados con seguridad y operación administrativa. Nunca deben añadirse secretos reales, archivos `.env` o datos de producción al repositorio.

## 4. Fases de trabajo

1. **Base limpia:** integrar el PR de `feature/v0.5.1-auth-hardening` en `main`, revisar CI y resolver observaciones.
2. **Diseño:** decidir los flujos de MFA/recuperación, el esquema de eventos y las reglas de autorización antes de programar.
3. **Backend:** completar servicios, validaciones, migraciones y pruebas.
4. **Interfaz:** implementar solo las vistas necesarias para las capacidades verificadas del backend.
5. **Calidad y seguridad:** ejecutar pruebas, lint, formato, auditoría y revisión manual del diff.
6. **Documentación:** actualizar los documentos aplicables y el changelog.
7. **Release:** preparar una versión candidata; crear la etiqueta `v0.6.0` y publicar solo con CI verde y autorización explícita.

## 5. Definition of Done

- [ ] Cada requisito tiene pruebas apropiadas.
- [ ] La autorización se valida en el servidor, no solo en la interfaz.
- [ ] Los secretos y tokens no aparecen en logs ni respuestas innecesarias.
- [ ] Las migraciones funcionan en bases de datos nuevas y existentes.
- [ ] `npm run check` pasa.
- [ ] La auditoría no reporta vulnerabilidades de producción de nivel alto o crítico.
- [ ] CI está verde para la rama candidata.
- [ ] La documentación y `CHANGELOG.md` están actualizados.
- [ ] El diff final no incluye cambios locales ajenos.
- [ ] La etiqueta y publicación se realizan solo con autorización explícita.

## 6. Riesgos y reglas de trabajo

- La implementación debe considerarse candidata hasta que pasen las pruebas, lint, formato y auditoría indicados en este plan.
- Las decisiones de recuperación deben aprobarse antes de implementarse; no se deben inventar políticas de seguridad.
- Los cambios de esquema requieren migraciones y pruebas.
- Los cambios de dependencias deben ser mínimos, justificados y verificados.
- Los archivos locales ajenos al alcance deben permanecer fuera del commit y del release.
- Si el alcance resulta demasiado grande, dividirlo en entregas menores.

## 7. Ubicación y mantenimiento

Guardar este archivo en:

`docs/roadmap/v0.6.0-plan.md`

Mantenerlo como plan específico de la siguiente versión. Actualizar su estado durante el trabajo y trasladar los cambios implementados y verificados al `CHANGELOG.md`. No marcar requisitos como completados solo por estar documentados.

**Resumen:** esta candidata implementa el ciclo operativo de MFA con códigos de recuperación de un solo uso, consulta administrativa paginada de eventos de seguridad y documentación asociada. No etiquetar ni publicar el release hasta ejecutar la auditoría de dependencias, validar CI y revisar el diff final.
