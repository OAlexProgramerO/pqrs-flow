# PQRS Flow — v0.7.0 Containerization Plan

**Status:** Planned; not implemented by this document  
**Current implementation baseline:** v0.6.0, merged into `main`  
**Proposed branch:** `feat/v0.7.0-containerization`  
**Previous milestone:** TOTP MFA, one-time recovery codes and administrator security-event auditing

## 1. Goal

Make PQRS Flow reproducible to build and run as a single-container application while preserving its current security boundaries and SQLite-based persistence. The goal is packaging and operational consistency, not multi-instance scalability or a claim of production readiness.

## 2. In scope

- Add a multi-stage Dockerfile based on a supported Node.js LTS image and a Debian slim runtime compatible with `better-sqlite3`.
- Install only production dependencies in the runtime image; do not copy development dependencies, Git history, local databases, `.env` files, test reports or Playwright artifacts into the image.
- Run the application as a non-root user with only the filesystem permissions required by the runtime.
- Add a `.dockerignore` that excludes secrets, local state, dependencies, coverage, browser artifacts and Git metadata.
- Add a Docker Compose configuration for local single-instance use, environment configuration and persistent storage for the SQLite database and uploaded attachments.
- Preserve the existing server health endpoint and configure a container health check that uses it without adding a runtime dependency unnecessarily.
- Document build, start, stop, upgrade, migration, log inspection, volume persistence and backup considerations.
- Ensure the TOTP encryption key, session secrets and SMTP credentials are supplied at runtime, never baked into image layers.
- Add CI checks to build the image and run a smoke test in the container without publishing an image or deploying the application automatically.

## 3. Out of scope

- Public cloud deployment, domain/TLS provisioning and production CI/CD publishing (planned for v0.8.0).
- Automatic database backup scheduling and managed off-site backup storage (planned for v0.8.0).
- Multi-instance/high-availability support. In-memory rate-limit counters remain process-local; Docker does not solve that limitation.
- Replacing SQLite, adding Kubernetes, introducing an ORM or redesigning the frontend.
- Claiming legal compliance or production readiness solely because the container builds or tests pass.

## 4. Required implementation artifacts

Expected files may change during implementation, but the initial proposal is:

- `Dockerfile` — reproducible multi-stage build and non-root runtime.
- `.dockerignore` — excludes credentials, local data, Git, dependencies and generated artifacts.
- `compose.yaml` — single-instance development/run configuration with named persistent storage and explicit environment variables.
- `.github/workflows/ci.yml` — image build and container smoke-test steps.
- `README.md` and `README.es.md` — current implementation and next planned version, Docker setup, persistence and operational limitations.
- `docs/security.md` — container-specific security notes and secret handling.
- `docs/architecture.md` or a new `docs/deployment.md` — runtime filesystem layout, volumes, migrations and operational commands.
- `CHANGELOG.md` and `ROADMAP.md` — update only after the implementation is completed and validated; this plan itself is not a completed feature entry.

## 5. Security and data requirements

1. The container must not contain `.env`, credentials, `data/pqrs.db`, WAL/SHM files, uploaded citizen attachments, or test data.
2. SQLite and attachment directories must be writable by the runtime user and stored in persistent volumes outside the container's ephemeral writable layer.
3. Document that SQLite database and attachment storage must be backed up consistently; a database-only backup is insufficient if attachments are needed to restore requests.
4. Keep MFA encryption material and session secrets external to the image. Explain that changing the MFA encryption key can make existing TOTP secrets unreadable.
5. Bind the published port intentionally and document HTTPS/reverse-proxy requirements, including `TRUST_PROXY` configuration.
6. Do not run more than one application process against this setup expecting in-memory rate limits to be shared.
7. Run as non-root, keep the image minimal, and do not add capabilities or privileged mode unless a demonstrated requirement exists.

## 6. Acceptance criteria

- A clean checkout can build the image using documented commands on supported Node/Docker versions.
- The container starts with only documented environment variables and returns a healthy response from the existing health endpoint.
- A request can be created, the server restarted/recreated, and the request remains available because SQLite is persisted.
- An uploaded attachment remains available after container recreation because its storage is persisted.
- The app runs as a non-root user and the image contains no `.env`, local database, attachment data, Git metadata or development dependencies.
- Database migrations run using the application's existing migration mechanism and do not require a manual schema edit.
- CI builds the image and executes a container smoke test without pushing it to a public registry.
- Existing `npm run check` passes, plus any Docker-specific checks.
- README English and Spanish, security docs, deployment instructions and changelog agree on the actual implementation status.

## 7. Suggested implementation sequence

1. Inspect runtime filesystem paths, startup/migration behavior, and `better-sqlite3` installation requirements.
2. Add `.dockerignore` and a first multi-stage Dockerfile.
3. Verify runtime user ownership and persistent paths for the database and attachments.
4. Add `compose.yaml` with explicit environment variables and named volumes.
5. Add container build and smoke tests to CI without registry publishing.
6. Update English and Spanish setup documentation and security guidance.
7. Run application tests, image build, health smoke test, persistence test, and a manual review of image contents.
8. Merge only after CI is green; create a `v0.7.0` tag only after release approval.

## 8. Risks and decisions to resolve during implementation

- Confirm the exact directory used for uploaded attachments and ensure both it and the SQLite database are persisted.
- Decide whether Compose should use an `env_file` example or only explicit variable mappings; never commit a real `.env`.
- Confirm health-check utilities are available in the chosen runtime image, or use a dependency-free Node-based check.
- Ensure the migration runner has write permission to the persistent database directory at first boot.
- Document the backup consistency relationship between SQLite and attachment files.
- Confirm the supported Node major matches the project's CI matrix and lockfile/native module behavior.

## 9. Definition of done

The v0.7.0 implementation is complete only when the acceptance criteria are verified in CI and locally. This planning document does not mean Docker support has been implemented, and no release tag or public deployment should be claimed based on this file alone.

## Implementation status

The local implementation adds a multi-stage `Dockerfile`, a scoped root `.dockerignore`, `compose.yaml`, root npm convenience scripts, a Docker-capable GitHub Actions smoke-test job, and matching English/Spanish container instructions. The runtime uses the existing backend lockfile, Node.js 22 on Debian slim, UID `10001`, a read-only root filesystem, named volumes for database and attachments, and the existing `/api/health` endpoint.

**Status: implemented locally; validation pending.** The implementation is not a release tag or GitHub Release. Do not mark v0.7.0 complete until `npm run check` and the Docker-capable CI job have both passed. Local Docker build and runtime results must be reported only if actually executed.
